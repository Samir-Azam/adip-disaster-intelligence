# ADR-006: S3-compatible object storage (MinIO for local/dev) for evidence files

## Status
Accepted

## Context
Citizens and field officers upload photo/video evidence attached to incidents. This is
untrusted binary user input that must never be stored inside the application database or
served directly from an unguarded filesystem path, and must be safely retrievable by
authorized users only.

## Decision
Store all uploaded evidence in an S3-compatible object store, accessed through the AWS
S3 SDK API surface. Use MinIO as the local/dev/CI implementation of that same API so the
adapter code is unchanged between environments; a real AWS S3 (or equivalent) bucket is
a drop-in swap via environment variables for a future production deployment.

## Alternatives considered
- **Store files on the Node server's local disk** — simplest for a demo, but doesn't
  survive container restarts/redeploys, has no signed-URL access control model, and
  doesn't reflect how this would actually be built in production. Rejected as not
  representative and operationally fragile.
- **Store file bytes directly in Postgres (bytea)** — avoids a second storage system,
  but bloats the database, hurts backup/restore times, and is a well-known
  anti-pattern for binary evidence at any real volume. Rejected.
- **Direct-to-cloud-provider SDK (not S3-compatible)** — locks local dev to needing
  real cloud credentials, breaking "runs fully locally via Docker Compose." Rejected.

## Consequences
- Every upload must be validated for MIME type and size *before* it reaches storage
  (see `06_SECURITY.md`), and stored under a generated, non-guessable object key — never
  the user-supplied filename.
- Access to evidence is via short-lived signed URLs generated by the backend after an
  authorization check, never a permanently public bucket/object.
- The `incident_evidence` table stores the object key and metadata (content type, size,
  uploader, checksum) — not the file itself — matching the DB design doc.
- Local/CI/dev all run against MinIO in Docker Compose; the only thing that changes for
  a real deployment is the S3 endpoint/credentials in environment variables, which must
  be documented but is explicitly *not* claimed as "production-deployed" by this project.
